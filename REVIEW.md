# Independent security & quality review — ARAG platform

Scope: `STANDARDS.md`, `README.md`, `docs/*.md`, everything under `src/`, `ui/`, `template/`, `scripts/`, `test/`.
Method: read every file listed above; verified the high-severity findings with `make check`, `make coverage`,
and small reproduction scripts run against the actual code (not just inspection) under
`/private/tmp/claude-502/.../scratchpad/review/`. Findings are marked **Verified** (reproduced) or **Plausible**
(code-path reasoning only, not exercised).

**Note on repo state:** the working tree has uncommitted changes to `src/http/app.ts`, `src/index.ts`,
`package.json`, `CHANGELOG.md` and `template/src/server.ts` (see `git status`/`git diff`) that already fix
finding #1 below (the `App.close()` idempotency bug). This review evaluates the *current working tree*
unless a finding explicitly says otherwise, and calls out where a finding is about the last commit
(`697d017`, v0.1.0) rather than the uncommitted fix.

| 2 | **Critical** | `src/http/app.ts:120-126` (`Ctx.ip`) and `:508-525` (`rateLimited`); exploited via `template/src/routes/admin.ts:27-36` (`adminLogin`) | **Verified.** `Ctx.ip` trusts the client-supplied `X-Forwarded-For` header whenever `Fly-Client-IP` is absent, with no allow-list of trusted proxies. The rate limiter buckets by `ip:${ctx.ip}`. Repro: burst of 2 requests (RPS=1, burst=2) from one client → `[200,200,429]` as expected; the same client sending 8 requests each with a *different* spoofed `X-Forwarded-For` value → `[200,200,200,200,200,200,200,200]`, i.e. **unlimited request rate**. Because `/api/v1/admin/login` and any `auth:"api"` route go through this same limiter, an attacker can brute-force `ADMIN_TOKEN` / `API_KEYS` at unbounded speed simply by rotating `X-Forwarded-For`. This is the platform's stated "security baseline" control (STANDARDS §5) and it does not hold outside a topology where a trusted edge proxy strips/overwrites that header (true on Fly.io for `Fly-Client-IP`, not guaranteed for `X-Forwarded-For`, and not true at all for `template/docs/architecture/deployment-topologies.md`'s other topologies, e.g. bare Docker). | Add a `trustProxy`/`ALLOWED_PROXIES` env setting; only honour `X-Forwarded-For`/`Fly-Client-IP` when the immediate peer (`req.socket.remoteAddress`) is in that allow-list, otherwise fall back to `remoteAddress`. | 5 | **Medium** | `src/store/jobs.ts:158-166` (`cancel`) and `:223-244` (`emit`) | **Verified by repro.** `cancel(id)` immediately calls `finish(id, "cancelled", …)`, which sets `job.status="cancelled"`, `job.message="cancelled"`, `job.finishedAt=…` and deletes the `AbortController`. It does **not** stop the still-in-flight stage's promise from eventually rejecting (e.g. a `fetch`/`waitProcessed` call that only reacts to `ctx.signal` asynchronously). When that rejection reaches `ctx.stage()`'s catch handler, it calls `emit(name, "error", {message})` unconditionally — `emit()` has no check for "is this job already finished?" — so it overwrites `job.message` (observed: flips from `"cancelled"` back to `"aborted"`), appends a new event to `job.events` **after** `finishedAt` was already recorded, and bumps `updatedAt` past `finishedAt`. | 6 | **Medium** | `src/store/jsonstore.ts:110-118` (`scheduleFlush`) | **Verified by repro.** Writes are buffered in memory and flushed to disk after a 50 ms debounce via `setTimeout(...).unref()`. `unref()` means this timer does **not** keep the process alive. In a long-running server this is masked because the listening socket keeps the event loop alive well past 50 ms, and the template's `index.ts:17-23` does call `store.flushAll()` (via `product.close()`) on SIGTERM/SIGINT — but any deployment that sends `SIGKILL` after a short grace period, or any crash/uncaught exception path, loses the last ≤50 ms of writes with no error surfaced anywhere. ## What's solid

- **Core HTTP toolkit correctness**: routing, auth precedence (admin-token → api-key → session → anonymous),
  problem+json rendering, body-size enforcement against both `Content-Length` and actual streamed bytes
  (protects against a forged/absent header), static path-traversal guard (the non-symlink case), and the
  request/response pipeline are all straightforward, well-tested, and behaved correctly under manual
  adversarial input during this review (traversal attempts, oversized bodies, malformed JSON, malformed
  multipart).
- **Session cookies**: `issueSession`/`verifySession` HMAC signing uses `timingSafeEqual` correctly and
  checks expiry; cookies default to `HttpOnly` + `SameSite=Lax` + `Secure` in production.
- **Secret handling**: the logger's `redact()` and `describeEnv()` consistently avoid printing full secret
  values in logs, and `AragError.toJSON()` deliberately excludes the upstream `detail` field so job records
  and error responses never leak ARAG's raw body or the KB token — this is applied consistently everywhere
  errors are surfaced to clients.
- **NDJSON/AskStream parsing**: `NdjsonSplitter`/`normaliseItem` correctly handle chunk-boundary splits,
  blank lines, malformed lines (capped diagnostics buffer), and both the current `{item:{…}}` envelope and
  legacy top-level shapes; cross-checked against `AskStreamItem`'s type union and the mock server's actual
  wire output (`retrieval → answer[/answer_json] → citations → metadata → status`) and found consistent.
- **AragClient timeout/abort**: `AbortSignal.any([userSignal, timeoutSignal])` composition, distinguishing
  timeout vs. user-abort vs. network error, and `withRetry`'s retryable-error classification are all correct
  and covered by `test/arag-client.test.ts`.
- **Test coverage**: `make coverage` (bypassing the currently-broken lint step) passes cleanly — 37/37 tests,
  95.84% line / 78.75% branch coverage on `src/`, comfortably over the 80%-line bar; the template's own
  integration suite (once the hang in #1 is fixed by the pending uncommitted change) passes 5/5 and exits
  cleanly.
- **Mock ARAG server**: binds to `127.0.0.1` only (both in tests and the standalone CLI), enforces the
  service-account header when an `apiKey` is configured, and its retrieval/answer heuristics are
  deterministic and reasonably faithful to the documented real-ARAG behaviours — a good, low-risk substitute
  for credentials-free CI.
- **Template scaffolding**: OpenAPI-first routes with real `minLength`/`maxLength` bounds on user input,
  `additionalProperties:false` on request bodies, consistent use of the `esc()` helper for all
  user-controlled data rendered into `innerHTML` across `admin.js`/`app.js`/`arag-ui.js` (no XSS found), and
  a non-root Docker user — all in line with STANDARDS.
